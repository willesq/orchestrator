Spaces: one open-source org, two employers, no bleed

How orch keeps two employers' GitHub orgs apart while sharing an open-source org everywhere. Everything orch ingests or shows from GitHub, local checkouts, sessions and chat feeds belongs to a space. orchd decides which space, and enforces it on every read without relying on the AI.

The scenario

  • oss-org an open-source GitHub org. Its docs should be readable from any session.
  • acme employer A's GitHub org, checked out under ~/work/acme.
  • globex employer B's GitHub org, checked out under ~/work/globex. Nothing may cross between acme and globex in either direction.
  • willesq your own repos under ~/code.

The org names are placeholders. In the policy you'd use real logins. Spaces cover Claude Code and Codex; no Google harness is in scope, and the existing Gemini adapter is reported as not covered (D-20).

Bottom line

  • A space is the unit of separation. Each space groups everything that belongs to one context: GitHub orgs, local folders, chat workspaces, and the terms that must not leave it. You'd have four: public acme globex personal.
  • Spaces come in three kinds. A public space is readable from everywhere but only accepts verified public content. An isolated space (each job) is readable only from inside itself, and by default reads only itself and public. A private space (personal) is like isolated, and may read other private spaces it lists. A job may opt in to reading a private space such as personal, never another job (D-16).
  • Two isolated spaces can never read each other. orchd refuses to apply a policy in which acme lists globex under reads, or the reverse (INV-04). The separation is a property of the space kind, not something you have to remember to leave out of a list.
  • The org that owns a repo decides its space. Not its fork parent, not where you cloned it, not what a session claims. A private repo inside the open-source org never becomes public, because orch checks GitHub's private flag on every sync.
  • Search isn't the only path between spaces. The session-start PR digest, PR monitoring, task lists, summaries and an agent running gh api against the other employer's org can all carry content across. Each is filtered or guarded by the session's space.
  • orchd decides the caller's space from the process tree, and only you can change space policy. The policy lives in orch.db as numbered revisions. An agent may save a draft, but it changes nothing until you review it and run orch spaces apply --revision N from your own terminal or the app (D-25, INV-06).
  • Each job has its own GitHub account. orchd makes every GitHub call for a job's orgs with that space's gh profile, so an acme credential never reaches globex (D-18, SP-063).

Config sketch

// spaces policy, stored in orch.db as numbered revisions (D-25).
// Save it as a draft:  orch spaces draft < policy.json
// Review it:           orch spaces diff
// Enforce it:          orch spaces apply --revision N   (operator only)
{
  "spaces": [
    { "name": "public", "kind": "public",
      "github_orgs": ["oss-org"],
      "web_prefixes": ["https://go.dev/", "https://docs.python.org/"] },

    { "name": "acme", "kind": "isolated",
      "github_orgs": ["acme"],            // case-insensitive
      "roots": ["~/work/acme"],
      "chat": ["slack:T0ACME"],
      "terms_file": "~/.config/orch/terms/acme.txt",
      "gh_config_dir": "~/.config/gh-acme" },  // you log in: GH_CONFIG_DIR=… gh auth login

    { "name": "globex", "kind": "isolated",
      "github_orgs": ["globex"],
      "roots": ["~/work/globex"],
      "chat": ["teams:globex.onmicrosoft.com"],
      "terms_file": "~/.config/orch/terms/globex.txt",
      "gh_config_dir": "~/.config/gh-globex" },

    { "name": "personal", "kind": "private",
      "github_orgs": ["willesq"],
      "roots": ["~/code"] }
  ],
  "public_root_sessions": "personal"     // where sessions under a public root write (D-22)
}

Field names match internal/spaces/policy.go; unknown fields are refused. A job opts in to reading personal with "reads": ["personal"] (D-16). There is no setting for private repos in a public org: they always go to quarantine.

Validation at apply time, which refuses the whole revision if any check fails and keeps the last applied one (SP-020):

  • An org, root, web prefix or chat tenant belongs to at most one space.
  • Roots may nest. The deepest matching root decides, like CODEOWNERS, and a nested root must be at least as strict as every root above it (public < private < isolated). A root of one job can't sit inside another job's root (D-15, INV-14).
  • An isolated space's reads can't contain another isolated space. A private space's reads can't contain an isolated space. A public space reads nothing else.
  • public_root_sessions must name a private or isolated space. If it's unset, orch uses the only private space if there is exactly one, else quarantine (D-22).
  • Term files live outside any git working tree.
  • Each org login is resolved through the GitHub API to its stable node ID, and orch stores both. A deleted org whose login someone else re-registers fails the ID check and its content goes to quarantine, not into your space. You confirm a changed ID with orch spaces apply --revision N --confirm-github-org <org> (SP-021).

Placing GitHub content

One rule covers every case: the org that owns the repo decides the space. orchd applies it to each kind of GitHub content:

What orch takes from GitHubWhere it lives todaySpace
Docs owner syncinternal/docs/sync.go, cloned into orch's cachethe owner's space, checked per repo for public spaces (next section). A job's orgs sync only through its own gh profile (SP-063).
PR monitoring, PR watch, attentioninternal/prs, internal/github scopesthe repo owner's space, stored on each cached PR
PR reviews and verdictsinternal/reviewsthe PR repo's space. The reviewer task runs located in it.
Repos and orgs listed for the GitHub screeninternal/github/identity.goshown to you in the app, filtered for agents
A fork: acme/oss-lib forked from oss-org/oss-lib—acme. The fork's owner decides, never the parent. Your employer's patches live there.
A repo transferred from oss-org to acme—moves at the next sync. Its chunks leave public before anything else is indexed (SP-030), and relabelling moves stored chunks to the new space (SP-027).
An org in no space—its content goes to quarantine, where you can assign it (internal/spaces/classify.go, SP-028). orchd's GitHub calls about it use your default gh login.

What makes something public

The public space is the one every session reads, so content gets in only by passing checks orchd makes against GitHub itself:

  1. The org is bound to a public space in applied config.
  2. GitHub reports the repo as not private at sync time. orch already lists repos with private (internal/github/identity.go:177). The docs sync's Repo type needs the same field. A private repo in oss-org, say oss-org/release-keys-infra, goes to quarantine. You can move it with an operator retag, orch spaces retag (SP-071).
  3. Visibility is checked again on every sync. If a public repo turns private, its chunks leave the public space in that sync, before anything else is indexed.
  4. Writers that aren't sources can't reach it. Sessions, summaries, edit hand-offs and rag_ingest_text are always homed to the caller's space. A session in an oss-org checkout writes to that checkout's root space, never to public. A session pinned under a root you declared public reads public only and writes to public_root_sessions (D-22).

Why sessions never go public: a session about an open-source repo still happens somewhere. If you're contributing to oss-org/oss-lib on acme's time from ~/work/acme/oss-lib, that transcript may contain acme context. Its space is the space of the folder it ran in.

Local checkouts and conflicts

Each checkout has two signals: the root it sits under, and the org in its git remote. orchd compares them whenever it places content from a checkout or pins a session in one.

CheckoutRoot saysRemote saysResult
~/work/acme/api → acme/apiacmeacmeacme
~/work/acme/oss-lib → oss-org/oss-libacmepublicacme for sessions and local files. The org's synced docs stay public. A public remote under a job root is allowed.
~/work/acme/billing → globex/billingacmeglobexconflict Nothing is indexed, sessions there get no space, and orch status flags it. Two isolated spaces disagreeing is never resolved automatically.
~/Downloads/x → acme/xno rootacmeacme. The remote alone places it in the org's space. This is safe because it can only narrow.
~/scratch/y, no remoteno rootnoneno space: sessions see public only, and writes go to quarantine

The conflict rule matters most. Copying a directory from one job's tree into the other's is exactly how bleed happens by accident, so orchd refuses rather than picking one.

Each job has its own GitHub account from the start (D-18). Each isolated space names a gh profile directory, gh_config_dir, which you log in to yourself with GH_CONFIG_DIR=<dir> gh auth login. orchd makes every GitHub call for that space's orgs with that profile, including docs sync, PR monitoring, reviews and org checks. It won't sync a job whose profile is missing or logged out, and orch status warns if one account can see another job's org. orch checks a profile only with gh auth status and never reads its tokens (SP-063). Agent sessions get the same GH_CONFIG_DIR from an orch-managed, uncommitted .claude/settings.local.json in each checkout, or from orch run <space> -- claude|codex (D-23, SP-046, planned). The gh/git guard is a second layer. Target extraction is best-effort, so the sandbox rules and separate accounts are the hard boundary (D-28).

How orchd verifies it

Nothing in this design takes the AI's word. orchd decides each of these itself:

Which space is this caller in?The kernel reports the peer PID. orchd walks the parent processes to the harness process registered at SessionStart and uses the space pinned for that session. The cwd in a request is ignored for access decisions.internal/daemon/callers.go, peer_darwin.go (LOCAL_PEERPID), procstat.Parent

Verified: orchd reads a process's start time and working directory on macOS (proc_pidinfo) and Linux (SP-003). How each harness's working directory moves was recorded (SP-001): Claude Code's shell returns to the project after a cd outside it, and Codex never keeps a cd. Pins record the harness PID plus its start time, so a reused PID doesn't match (SP-010). Still open: binding the peer PID to its connection (RC-03), and gating pin-based reads until the guard stops a session from starting a harness outside its tree (RC-01, RC-26).

Scenarios

"How do we deploy?" in acme

A session in ~/work/acme/api asks a question that matches docs in both jobs.

acme and public hits only. globex's deploy runbook doesn't exist as far as this session can tell, including in listings.

Pasting globex text into an acme session

You quote a globex snippet into an acme prompt by mistake.

Search still returns nothing from globex, but the transcript now contains it and is stored as acme. This is a human mistake orch can't undo. The terms guard keeps globex's terms out of anything acme sends outward.

An open-source repo goes private

oss-org/tooling is made private.

The next sync sees private: true and moves its chunks out of public before indexing anything else. Sessions everywhere stop seeing them.

You leave acme

not yet planned No feature in the plan retires a space.

A retire command would delete acme's collection, cached PRs, tasks and events and keep its term list as an outbound guard, leaving globex untouched. Each space has its own collection (D-10), which makes this a whole-collection delete.

acme acquires globex

not yet planned The plan names an explicit operator merge but no feature builds it.

Changing a reads list can't do this, because isolated spaces can't list each other. A merge would move globex's points into acme's collection without re-embedding, as a retag does (SP-071).

Dispatching a task from acme

An acme session queues a dev task.

Planned (SP-029): the task record carries acme. The task runs in acme's checkout and searches as acme. Its PR, review and result events stay in acme. How tasks orchd doesn't track get a space is still open (RC-25).

Fail-closed rules

  • A caller whose space can't be established sees public only.
  • Content that can't be placed goes to quarantine, never to public.
  • A repo's visibility can't be read → it's treated as private.
  • An org's node ID doesn't match the one stored when it was bound → the space binding is suspended for that org until you confirm it.
  • A root conflicts with a remote across two isolated spaces → no space and no indexing, and the conflict is flagged.
  • Config fails validation → orchd keeps the last applied config and reports why.
  • While the tool guard or outbound terms layer is enforcing, a timeout, unreadable pin or unreadable policy → refuse (INV-13).
  • You can switch each layer (memory filtering, tool guard, outbound terms, sandbox rules) off or between modes, optionally for a set time, as operator only. Every change is logged, logging continues, and while any layer is off every session's start digest says so (D-11, SP-070, INV-16).

Decided

  1. Can a job space read personal? Only by opting in: a job lists personal in its reads. It's off by default and never extends to another job (D-16).
  2. Where do web pages go? The writer places them at ingest. A page a session ingests takes that session's space. Allowlisted prefixes reach public from sources refresh. You can retag any source, which moves its data without copying it (D-14, SP-030, SP-071).
  3. One GitHub account per job, or guards? One account per job from the start, with the gh/git guard as a second layer (D-18, SP-063).
  4. Nested roots? Allowed, CODEOWNERS-style: the deepest matching root decides, and a nested root is never less strict than the roots above it (D-15).
  5. Where you see everything? The app shows all spaces at once, labelled, with a one-click screen-share-safe mode that hides all but one space (D-21).

This builds on memory-permissions-design.html: a space is that doc's single "home", and the public kind is its shared. Compartments from that doc would only be needed if one chunk must belong to two spaces at once, which isolated spaces rule out.

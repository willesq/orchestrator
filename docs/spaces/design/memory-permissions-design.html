Who may read what: a permission model for orch's memory

Updated 2026-11-09 to match the plan. The authoritative plan is docs/spaces/spaces-features.json (rendered at docs/spaces/index.html); where they disagree, the plan wins.

A design for keeping two employers' work, open-source work, personal work, and future chat feeds (Slack, Teams) apart inside one orch memory store. It started from #130 (memory partitions) and folds in the unbuilt docs/RAG_SENSITIVITY_PLAN.md. The first draft proposed compartments and sensitivity levels. The plan settled on spaces: one space per chunk, one Qdrant collection per space. This page describes that model and keeps the rejected options as a record of why.

Bottom line

  • Store facts and a space on chunks. Keep policy out of them. orchd stamps each chunk with where it came from (its origin). A pure classifier turns origin into exactly one space, or quarantine. The caller's pinned space decides what it may read. Each layer can change without the others (SP-022, SP-023).
  • A space is the unit of separation (D-08). Its kind is public (readable from every space), isolated (one per job, never reads another isolated space) or private (personal). A space owns bindings: GitHub orgs, folder roots, web prefixes, chat tenants, an outbound terms file and a gh profile.
  • One space per chunk, one Qdrant collection per space, plus collections for public and quarantine. The payload also stores space as a second layer, and searches fuse the readable collections with RRF (D-10, D-24).
  • Sensitivity within a space is a per-content-kind rule, not a level. DMs are stored and searchable on request, but never auto-recalled and never given to tasks (SP-060, D-19).
  • Feeds plug in through a common origin schema (system, tenant, container, container kind, participants). Slack and Teams then need a connector and a tenant binding, not a model change (D-07, SP-060).
  • Redrawing boundaries is a relabel, not a re-ingest. Chunks labelled under an older policy fail closed until orch rag relabel moves them to the right collection without new embeddings (INV-08, SP-027). Single sources move with a retag (D-14, SP-071).
  • Outbound checks look at the destination, not the session. A term from a space is refused in any action whose target repo's owner doesn't belong to that space (SP-044).
  • Memory is one layer of several: a pre-tool guard, OS sandbox deny rules, a separate GitHub account per job and git hooks back it up (D-04, D-18, D-23).

From partitions to spaces

#130 gives every chunk exactly one partition, chosen by longest-prefix match on a filesystem root. The first draft of this design argued that this breaks once feeds arrive, and proposed several compartments per chunk. The plan kept one label per chunk and answered the two objections differently:

Content belongs to more than one world

  • A Slack DM with a coworker about your side project.
  • A session in a job's folder that pulled in personal notes, then got summarized.

Resolved: the writer places content (D-14). A chat message takes its tenant's space, and a session's output takes the session's space (SP-029). Content shared by two jobs is exactly what must never exist (INV-04), so combining two jobs is an explicit operator "merge". "Most restrictive" now has an ordering: public < private < isolated.

Not everything comes from a folder

  • GitHub-owner docs sync clones into orch's own cache (internal/docs/sync.go), outside any user root.
  • web sources are URLs.
  • Slack and Teams have workspaces, tenants and channels, not paths.

Kept: root matching is one binding among several. A space binds github_orgs, roots, web_prefixes and chat tenants (SP-020).

Sensitivity also cuts across worlds. A personal DM and an employer DM should both stay out of auto-injection. The plan handles that per content kind inside each space (SP-060, SP-052's Recall step, SP-053's per-content-kind policy table), not with a second label dimension.

Should we tag chunks or tag spaces? Both, for different jobs. Chunks carry a space (where this content belongs). Spaces are named policy objects that carry attributes: bindings, which other spaces they read, a terms file, a gh profile. Never let a chunk's descriptive tags imply access. That separation is what lets you redraw policy without touching content.

Clients can't choose a space. A client-supplied space or a tag claiming one is ignored, and a client Ingest is placed in the caller's pinned space or quarantine (SP-023 a3, INV-02). trust stays server-assigned by writer, as today.

The model: spaces

Readable if and only if:

chunk.space    ∈ reader.readable_spaces   # own space + public + private spaces it lists in reads
chunk.labels_v = current policy's        # else unreadable until relabelled (INV-08)

No caller reads quarantine. With no policy applied, every chunk and caller is in one implicit shared space, so behavior is unchanged (INV-10, internal/spaces/policy.go).

Roots nest like GitHub CODEOWNERS: the deepest matching root decides, and a nested root may only be at least as strict as every root above it, for example ~/code public, ~/code/willesq private, ~/code/company1 isolated (D-15, INV-14). When a checkout's root and its git remote disagree, the stricter one wins. Two different isolated spaces disagreeing is a conflict: nothing is indexed and a session there gets no space (SP-022).

Considered and rejected: compartments plus levels. The first draft gave each chunk several compartments and a level (normal < private < secret), readable when the reader held every compartment and a high enough level. The plan chose one space per chunk instead (D-08): placement by writer (D-14) and explicit merges replace multi-world chunks, and per-content-kind rules replace levels (SP-060, D-19). One space per chunk is also what makes a collection per space possible without duplicating content.

How it maps onto Qdrant

Each space has its own collection, plus one for public and one for quarantine (D-10). Writes route by space. A search queries only the caller's readable collections, applies a space payload filter inside each as a second layer, and fuses the results with reciprocal rank fusion. Migration, reindex, backup and hybrid tooling work per collection, and every content or embedding cache is keyed by space (SP-024, INV-11).

The cost was measured, not assumed (SP-002): on 40,000 chunks, searching two of four collections and fusing them is 1.5× (2 segments) to 1.9× (default segments) the p95 of one filtered collection, about +15 ms per hybrid search. D-24 accepts that cost. Physical separation means a forgotten filter can't leak across spaces, and BM25 statistics don't mix spaces.

The first draft's single-collection filter relied on Qdrant match.except semantics over an array of compartments. With a single-valued space that question no longer matters for the design, although RC-15 still lists it with the GetDocument and session-recall handlers to check before SP-025.

Resolution is not yet trusted to grant reads. SP-025 must not grant reads by pin or operator resolution alone until the guard (SP-041) or stronger kernel evidence covers these (RC-01).

The spaces policy

There is no config.yaml (removed in PR #142). The policy is a JSON document stored in orch.db as numbered revisions with a content hash: drafts and the applied one (D-25, SP-020). Its schema is internal/spaces/policy.go; unknown fields are refused.

{
  "spaces": [
    {"name": "oss",      "kind": "public",   "github_orgs": ["oss-org"], "roots": ["~/code"]},
    {"name": "personal", "kind": "private",  "github_orgs": ["willesq"], "roots": ["~/code/willesq"]},
    {"name": "acme",     "kind": "isolated", "github_orgs": ["acme"],    "roots": ["~/code/acme"],
     "web_prefixes": ["https://wiki.acme.example/"], "chat": ["slack:T0ACME"],
     "terms_file": "~/.config/orch/terms/acme.txt", "gh_config_dir": "~/.config/gh-acme"},
    {"name": "globex",   "kind": "isolated", "github_orgs": ["globex"],  "roots": ["~/code/globex"],
     "chat": ["teams:contoso.onmicrosoft.com"], "reads": ["personal"],  # opt-in (D-16)
     "gh_config_dir": "~/.config/gh-globex"}
  ],
  "public_root_sessions": "personal"   # session content pinned under a public root (D-22)
}
orch spaces draft < policy.json    # save a draft (changes nothing)
orch spaces diff                   # compare the draft with what is applied (operator only)
orch spaces apply --revision N     # enforce draft N (operator only)
orch spaces why <target>           # where a path, URL, owner/repo or slack:/teams: tenant goes, and why

Notes on the shape:

  • Writer bindings and reader permissions are separate. Bindings say where content goes; reads says what a space may read. #130's readable_from merged them.
  • Validation rejects an org, prefix or tenant bound twice, the same root bound twice, a nested root less strict than one above it, an isolated root inside another isolated space, isolated reading isolated, private reading isolated, public reading anything else, and a terms file inside a git tree (SP-020.1, INV-04, INV-14).
  • Only the operator applies, naming the revision they reviewed. Any caller except a queued task may save a draft; applying an agent's draft needs --accept-agent-draft. A pending draft, or an applied row edited outside orchd, shows as drift and changes nothing enforced (D-25, INV-06).
  • GitHub orgs are bound by node ID at apply (--confirm-github-org). A mismatch on a later sync suspends the binding and quarantines new content until the operator confirms (SP-021).
  • Each job space names its own gh profile (gh_config_dir), used for that space's docs sync, PR monitoring and reviews. The user logs in with gh; orch never handles the token (D-18, SP-063).
  • Quarantine, not shared. An unplaceable write goes where nothing can read it, and orch status shows the count (INV-03, SP-028, SP-031).
  • Root paths may start with ~ and must otherwise be absolute. Resolving root symlinks before the nesting checks is a follow-up (RC-11).

Considered and rejected: an ordered rule list. The first draft matched origin with ordered rules (path, github_owner, url_prefix, tenant, container_kind, participant, writer, kind) that unioned compartments and raised levels. The plan replaced it with per-space bindings, deepest-root-wins nesting and stricter-of-root-and-remote (D-15, SP-022), and one override per source from retag (D-14).

Connector rules:

  • A connector reports facts and never decides placement. The Slack connector says "this is a DM in workspace T0ACME". It can't set space or level fields (SP-060 a3). Classification stays in one place.
  • Identify by stable IDs, not display names. Channels get renamed and tenants get rebranded. Display names may sit in the text but never in origin fields the classifier reads.
  • Connectors are opt-in per container. Sync only what you allowlist (DMs, selected private channels) rather than everything the API can reach. Retention is per space and content kind (SP-060).
  • Source URIs carry the system (slack://<tenant>/<channel>/<thread>, teams://…), so the existing per-URI dedupe, replace and delete keep working.
  • Listing paths are read paths. ListSources, ListDocs and rag_list_sources return URIs and titles, which can name a channel, customer or repo. They get the same space decision as content search (SP-025, INV-01).

Derived content and taint

Summaries, session records and anything else orch writes from other memory must not launder the space. Derived content carries the space of what it came from (INV-09, SP-029):

  • Summaries are made from one session at a time and inherit its space. The summarizer never receives text from two sessions in one call.
  • Task records carry the dispatching session's space, and tasks run pinned to it (still open as RC-25).
  • Files a session writes outside any root (for example in /tmp) are recorded with the session's space, and a later ingest of them uses it.
  • The operator's explicit cross-space reads taint that session.

Because a session can only read its own space, public and its listed private spaces, the first draft's union-of-every-input taint set and its per-session versus per-turn question no longer arise.

Changing the boundaries later

This is why origin and space are separate fields. The space is derived data and can be recomputed at any time.

  1. Draft and apply a new policy revision (D-25). Nothing changes until the operator applies.
  2. Stale chunks fail closed at once. A chunk whose labels_v isn't the current policy's is unreadable until relabelled (INV-08). This mirrors how bm25_v marks keyword vectors stale in internal/rag/reindex.go.
  3. orch rag relabel moves stale chunks into the right collection, using stored origin, source_uri, checkout tags and the session table. No new embeddings, and it resumes after interruption. Unplaceable chunks go to quarantine (SP-027).
  4. Preview first. orch rag relabel --dry-run prints counts per transition and space names, never content.

Outbound: terms and destinations

#130 asks whether the session's partition allows a term. A better question is whether the destination allows it. Your employer's name belongs in your employer's PRs. The same name in a public personal repo is the leak.

  • Terms attach to spaces. Each space may name a terms_file: one term or re:<regex> per line, case-insensitive, word boundaries. A terms file inside a git tree is refused (SP-044, SP-020).
  • The destination is the target repo's owner, mapped to a space through github_orgs; there is no separate destinations config. An action is refused when its text contains a term from a space the destination doesn't hold (SP-044).
  • Covered actions: git commit message and staged diff, git push range, git tag -m, gh pr and gh issue create/edit/comment/review, and gh api writes.
  • The pre-tool guard is the primary check (SP-044 runs in the guard from SP-040/041). Git hooks back it up: orch guard git-hook --install adds commit-msg and pre-push hooks that run the same check for any committer, including your own terminal (SP-045).
  • Refusals never echo the term. They give the term's line number and hash, never the term, and terms never appear in logs, transcripts, the UI or indexed content (INV-07, SP-048).

Representation options compared

S

One space per chunk, one collection per space

Chosen (D-08, D-10, D-24)

The model in this document. Origin facts on each chunk, one space from the classifier, a collection per space with a space payload filter as the second layer, the caller's readable collections fused with RRF.

For

  • A forgotten filter can't leak across spaces, and BM25 statistics stay per space (SP-024).
  • Redrawing boundaries is a relabel or retag, never a re-embed (INV-15).
  • Feeds plug in through origin fields and bindings.

Against

  • Measured search cost 1.5–1.9× p95, about +15 ms (SP-002, accepted in D-24).
  • Migration, reindex, backup and caches must work per collection (SP-024.2).
  • Content can't belong to two spaces; it is placed by writer and moved by retag.
Re-embedding neverNew feeds connector + binding
R1

Compartments + level, derived from origin

Not chosen

The first draft's recommendation: several compartments and a level per chunk, a subset-and-level filter in one collection.

For

  • Expresses content in two worlds, and sensitivity within one.
  • One Qdrant filter in buildFilter.

Against

  • The plan chose spaces (D-08) and physical separation (D-10); multi-compartment chunks can't live in one collection per space without duplication.
  • More concepts: workspace, rules, level, union taint.
  • Depended on unverified match.except semantics (RC-15).
R2

Single partition per chunk (#130 as written)

Basis of the chosen model

One partition string per chunk, assigned by root prefix, with readable_from lists.

For

  • Simplest to explain and build.
  • The chosen model keeps its one-label-per-chunk shape.

Against

  • Root matching alone misses docs owners, URLs and chat tenants; spaces add those bindings.
  • Mixed writer rules with reader permissions; spaces separate bindings from reads.
R3

Materialized reader list on each chunk

Not pursued

Store readable_by: [ctx-a, ctx-b] on each chunk and filter with match any [my context].

For

  • The cheapest possible filter.

Against

  • Every reader change means a relabel, even when no content changed.
  • Collection routing makes it unnecessary.
R4

A Qdrant collection per compartment

Adopted, per space (D-10)

The first draft kept this for secret only, because it can't hold multi-compartment content. With one space per chunk that objection falls away, and the plan adopted it for every space.

For

  • A filter bug can't leak across collections.
  • Moving a source is a copy, verify and delete (SP-071).

Against

  • Multiplies migration, reindex, backup and cache tooling.
  • Cross-collection ranking needs RRF, at the measured cost.
R5

Reuse descriptive tags for access

Don't

Add tags like partition:employer to the existing tags field and filter on them.

For

  • No schema change, and the tag index already exists.

Against

  • Clients and agents set tags today, so anyone could grant themselves access. A tag claiming a space is ignored (SP-023 a3).
  • Mixes search hints with security.
Risk high
R6

A general policy engine (Cedar, OPA)

Not now

Express rules in a policy language and evaluate them per request.

For

  • Arbitrary conditions, and well-tested evaluators.

Against

  • Qdrant needs a collection choice and filter before retrieval, so policy would compile down to those anyway.
  • A new dependency and language for a single-user tool. OpenAPPA's patterns are copied instead, not the component (D-13).

Every layer (memory filtering, tool guard mode, outbound terms, sandbox rules) has an operator-only switch, optionally timed. Turning a layer off is logged and announced in every session's start digest, and logging continues (D-11, SP-070, INV-16).

Fail-closed rules

  • A labels_v that isn't the current policy's → unreadable (INV-08).
  • Content that can't be placed → quarantine, never public (INV-03).
  • Root and remote in two different isolated spaces → conflict: nothing indexed, the session gets no space (SP-022).
  • A session with no space → public only (SP-025).
  • A later cwd never changes the session's space. The first pin wins (INV-05).
  • Unreadable repo visibility → treated as private (SP-030).
  • A GitHub org whose node ID changed → binding suspended, new content quarantined (SP-021).
  • While the guard is enforcing: timeout, unreadable pin or unreadable policy → refuse (INV-13).
  • An invalid draft → rejected at apply; the last applied revision stays in force (INV-04, SP-020).
  • A terms file inside a git working tree → rejected (SP-020).

What this does not protect

  • Files on disk, fully. The tool guard and generated sandbox rules narrow it, but tool-call target extraction is best-effort (D-28, RC-37, RC-38). The OS sandbox and per-job GitHub accounts are the hard boundary. Codex can still write the shared /tmp from every space (RC-09).
  • A hostile local process. Anything running as you can call the orchd socket, start a fake harness under a kept-alive parent (D-26), or read Qdrant's data directory. Pinning and lineage checks raise the bar against a confused agent, not a determined attacker.
  • The model provider. Anything injected into a session goes to the harness's provider under that account's retention terms.
  • Paraphrase. Term matching is a tripwire. It won't catch "a large Seattle retailer".
  • Feed-side permissions. If you can read a Slack channel, the connector can too. orch doesn't re-check the source system's ACLs after ingest, so retention per space and kind matters (SP-060).
  • Other harnesses. Spaces cover Claude Code and Codex only; the Gemini adapter is reported as not covered (D-20).

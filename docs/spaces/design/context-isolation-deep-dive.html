Bottom line

  • OpenAPPA is the closest prior art, but don't adopt it as a component yet. It's a well-designed information-flow-control engine (about 12 weeks old, MIT, Rust, weekly breaking releases). Its labels, audience × trust, map almost directly onto orch's space × trust. But it has no memory or RAG concept, no tenancy, an unauthenticated loopback /hook, and Bash coverage that depends on patching each Claude Code release. Copy six of its patterns now, and design orch's labels so an OpenAPPA integration could come later. Adopted as D-13; the optional label source is SP-064.
  • The research changes one earlier recommendation: give each space its own Qdrant collection. Qdrant's own guidance is to use separate collections for a small number of tenants that need strict isolation, which describes your spaces. Isolated spaces never share chunks, so the main objection to collections (content in two spaces at once) no longer applies. A forgotten filter on some future RPC then can't leak anything, and BM25/IDF statistics stop crossing spaces. The payload filter stays as a second layer. Adopted as D-10; the measured search cost was accepted in D-24.
  • Your directory-pin idea is right, with one adjustment: pin the space, not the exact folder (D-09). The first cwd at SessionStart fixes the space for the session's life (INV-05). The hook cwd is not a reliable record of later moves: SP-001 found that Claude Code undoes a cd outside the project after the call yet still fires CwdChanged, and that Codex keeps no cd between calls and has no CwdChanged. The guard therefore judges each call's own cwd and targets. Moving within the session's space (api → web, both acme) is normal and stays allowed. Reaching into another isolated space is refused, whether by cd, an absolute path, git -C or gh.
  • Parsing cd alone can't make it uncircumventable. cd x && … in one command, absolute paths, scripts and subprocesses all slip past text checks. The guard therefore checks every target of a tool call, not just directory changes. Target extraction is best-effort, not a complete analysis of shell (D-28). The OS sandbox deny rules for the other job's folders (SP-046) and a separate GitHub account per job (SP-063) are the hard boundary. Each layer covers gaps in the others.
  • The command log is cheap and bounded. About 150 KB per typical session. It lives in its own owner-only file, toollog.db (D-29), and is kept until 7 days after the session ends, where "ended" comes from the kernel rather than hook events (SP-015, SP-017). It's hash-chained, redacted, and never indexed into memory (INV-12).
  • Enforce from the first release (D-11). Phase 1 ships the hooks, the log and the enforcing guard together, replacing the log-only first phase this document first proposed. Each enforcement layer has an operator-only switch (the guard's states are off, log, block-other-jobs and strict), optionally timed. While any layer is off, every session's start digest says so, and logging never stops (SP-070, INV-16).

OpenAPPA from the source

Read from a shallow clone at acb9853 (8 Nov 2026). None of its code was run. The key claims below were checked directly in the files.

Aug 2026created. About 955 commits, 18 contributors, releases v0.36–v0.39 weekly. README: "preview & RFC".
MITcore licence. The Archestra platform that embeds it is commercial and dual-licensed.
~157k LOCRust: appa-engine (~50k) and appa-runtime (~107k), plus Python "batteries".

What it is

APPA (Agentic Permissions Policy Algebra) is an information-flow-control engine that sits between an agent and its tools. Before each tool call it asks: may a value derived from these sources flow into this sink?

HarnessClaude Code, opencode, amp, kagent
Adapterappa hook: translates JSON, no policy
Runtimeaxum on 127.0.0.1:8787, /hook /mcp
Enginepure function over the event log: no IO, no clock
Event logSQLite, append-only, compare-and-swap, policy revision stamped

What it doesn't do

  • No caller authentication on /hook. Being loopback-only is the whole of its access control (appa-runtime/src/main.rs:395). Any local process can post events for any session. orchd's kernel peer-PID and process-tree identity is stronger.
  • No tenants. One runtime serves one config, with a single internal rung. Two employers would be two groups or two deployments, and storage isn't partitioned.
  • No memory or context-store isolation. It doesn't inspect the prompt text and has no concept of RAG.
  • Fragile Bash coverage. It relies on a BUN_OPTIONS preload into Claude Code that has to be vetted for each release, or on SafeBash. Without its launcher, Bash calls are refused.
  • Probabilistic edges. The fallback annotators and the redact-for-public sanitizer are LLM calls, which the policy itself labels as unverified.

Can orch use OpenAPPA?

A1Copy its patterns into orch

Do now
  • A pure decision function over an append-only event log, with replay tests. The space guard becomes Decide(policy, sessionPin, toolEvent) → verdict with no IO. Recorded tool events become CI fixtures (orch spaces replay), so a policy change is tested against real sessions.
  • Stamp the policy revision on every decision and store policy content-addressed, so the log says which rules refused what.
  • Self-protection paths. The guard refuses agent writes to orch's config and data directories, ~/.claude/settings*, ~/.codex/hooks.json, Gemini settings and git hooks. Otherwise an agent could simply remove orch's hooks.
  • Label files on write. A file an acme session writes outside any root (say /tmp/notes.md) records acme. A later ingest of that file goes to acme, not quarantine or shared.
  • Map org membership explicitly. Their "unrelated orgs never imply internal" is the same rule as orch's isolated kind.
  • Isolate any LLM that orch runs internally. The session summarizer gets one session's content only, a schema-bound output, and no tools. Its output inherits that session's space.

In the plan: the decision function (SP-040) and replay (SP-047), policy_rev on every logged event (SP-014) and content-hashed policy revisions (D-25), self-protection paths (SP-042), files written outside any root and summaries carrying their session's space (SP-029), and confirmed org bindings (SP-021).

A2Make orch an OpenAPPA label source

When its wire format stabilises

OpenAPPA calls "externals" (annotators and audience sources) over HTTP or as a command. orch could ship one that labels the results of rag_search and other orch MCP tools with their space and trust. Someone running OpenAPPA would then get information-flow control across orch memory, and orch would gain sink checks (no acme-derived text into a public PR) without building them. To keep this possible, keep orch's chunk labels shaped as space × trust and expose them on every hit, which trust already is.

In the plan: SP-064 (Phase 5, optional), gated on OpenAPPA reaching a stable wire format and ideally authenticating /hook callers. The user decides then whether to build it or defer it (D-13).

A3Embed or require OpenAPPA as orch's enforcement layer

Not now

Rust with no Go or C bindings (the napi bindings live in Archestra), so it would be a second daemon. Its wire format breaks weekly. Its /hook is weaker on identity than orchd. Its Bash story is specific to Claude Code, while orch also supports Codex and Gemini. And it doesn't address memory, which is orch's core problem. Revisit when it reaches 1.0 or adds caller authentication.

Convergence worth noting: OpenAPPA's audience × trust and orch's space × trust are the same two-dimensional label. orch already stores trust per chunk, assigned server-side by writer. Adding space keeps the two systems composable.

Directory pin and command log

Your proposal: a pre-tool hook records every command, detects directory changes, always respects the first directory, and makes the pin impossible to get around. Here's how to build it so it holds up.

SessionStartfirst cwd → space, pinned by orchd (SP-010)
PreToolUseevery tool call, before it runs
Extract targetscwd, file paths, cd/git -C/gh -R, absolute paths; best-effort (SP-013, D-28)
Decidepure function: policy × pin × enforcement state × event (SP-040)
RecordRecordToolEvent to orchd, hash-chained in toollog.db (SP-014)

What "respect the first directory" means

  • The first cwd fixes the session's space for its lifetime, including resume, compact and subagents (INV-05). No later event, hook payload or request field can change it. A resumed session in a new process rebinds the pin to the new PID but keeps its space (SP-017).
  • Moving within the space is allowed and logged (~/work/acme/api → ~/work/acme/web). Agents do this constantly for monorepos and sibling repos.
  • Reaching into another isolated space is refused at the tool call that would do it (SP-040). A cd that leaves the project does not carry over in either harness: Claude Code undoes it after the call and Codex never keeps it (SP-001). Each call is therefore judged by its own cwd and targets, not by a tracked current directory.
  • Moving to no space (/tmp, a build cache) is allowed and logged in the default mode. Strict mode, which is opt-in, refuses it (D-12).

Why it checks targets, not just cd

  • In cd ~/work/globex && cat x, PreToolUse sees the cwd from before the command. The cd is inside the command.
  • cat ~/work/globex/x never changes directory at all.
  • git -C, make -C, env -C, pushd, and subshells.
  • bash -c "…", scripts and python -c can construct paths at runtime that no text check sees. That is the job of the OS sandbox layer.
  • Extraction is best-effort (D-28). Forms it can't read, such as eval, python -c or unknown variables, are flagged opaque, and SP-040 decides what each guard state does with them. A path that is an ancestor of another space's root (grep -r ~/code) must count as reaching into it. Both are open in RC-36; known limits are in RC-37 and RC-38.

The hook contract changes. internal/hook/hook.go promises that a hook never blocks the session. The guard is a documented exception (SP-041). While it is in an enforcing state it fails closed: a timeout, an unreadable pin or an unreadable policy means refuse (INV-13). In the off and log states it always allows. To keep that from bricking sessions, the guard decides locally in orch-hook from two read-only files orchd writes: the applied policy plus enforcement state, and the session pin. It doesn't wait on an orchd round trip, and the self-protection rules stop agents from writing to either file (SP-042).

Logging is a separate path. Each event goes to orchd through the RecordToolEvent RPC with a 20 ms budget (internal/hook/tooluse.go). Events dropped from orchd's full intake queue are counted in a "gap" record in the session's chain (D-30). A file spool was rejected because it can't carry the caller's process identity (RC-30), so events lost while orchd is down are accepted while the guard only logs.

Size and retention

  • Volume: a long session makes about 300–600 tool calls at about 300 bytes each, roughly 100–200 KB. A busy week is a few tens of MB.
  • Retention: deleted 7 days after the session ended (configurable: 3, 7 or 30 days). "Ended" comes from the kernel, not hook events: SessionEnd, or the pinned harness process gone or replaced, noticed within a minute (SP-015, SP-017).
  • Idle sessions: a session whose process is still alive is never treated as ended, however long it has been idle. Its log is capped at 50 MB instead, oldest non-refusal records first (SP-015).
  • Hard cap: a total size cap (default 500 MB) deletes the oldest ended sessions first, so a runaway session can't fill the disk (SP-015).
  • Refusals kept longer: refusal records alone are kept 90 days, so a pattern of attempts stays visible.
  • Who sweeps: orchd (SP-015, not yet built). Hooks only append.
  • Stored in its own SQLite file, toollog.db in orch's data directory, created 0600 together with its -wal and -shm files. It stays out of orch.db and its backups (D-29, SP-014). Self-protection rules cover it (SP-042).
  • Who is logged: only events orchd can attribute to a pinned session or a running task. Events from an unpinned harness or the operator are counted and dropped (open: RC-43). A queued task's events are logged under the task orchd resolves, never the session_id the request names (D-31).
  • Never indexed into RAG. It's evidence, not memory. Commands can quote another job's paths, and indexing them would itself leak.
  • Redacted through internal/redact before it's written. A refusal for an outbound term gives the term's line number and hash, never the term (SP-044, INV-07).
  • Hash chain per session (SP-014). It detects modified, deleted and reordered records, and the chain head is anchored at SessionEnd. The anchors currently live in toollog.db itself, so records removed after the last anchor, or a chain rewritten from its first record, can't be detected. Task chains are never anchored, because tasks send no SessionEnd. Where to anchor is open (RC-42). As Crosby & Wallach note, this proves tampering only relative to an anchored head. It doesn't stop the local user.
  • The pin itself lives in orchd (SP-010): session id, harness, harness PID and start time, first cwd, main checkout, space, policy revision, pinned_at and ended_at. Pins survive hook crashes and can be checked from the app. Pins grant no memory access yet: a process started outside a session's tree can take its own pin (D-26), and pin-based reads wait on RC-01.

Layers 3 and 4 need settings that differ by space. SP-004 measured how they layer (docs/internals/install.md). In Claude Code, the checkout root's settings.local.json applies anywhere in the checkout, but the root settings.json applies only when a session starts in the root. Sandbox denyRead alone doesn't stop the Read tool, the single-slash Read(/…) form doesn't block, and a fresh CLAUDE_CONFIG_DIR starts logged out. Codex has no per-checkout path for its profile.

D-23 delivers both options (SP-046). orch keeps the root .claude/settings.local.json of every checkout under a space's roots. It holds sandbox.enabled, allowUnsandboxedCommands: false, the Read(//…) and Edit(…) denies, and GH_CONFIG_DIR. The optional launcher orch run <space> -- claude|codex gives a session the space's full profile from any folder. A launcher profile needs its own Claude login, and Codex coverage depends on the launcher.

The way forward

The phases follow spaces-features.json as of 9 Nov 2026. They replace the phases first proposed here, which started with a log-only period (superseded by D-11).

  1. Phase 0: verify the assumptions. Done. Real hook payloads for Claude Code and Codex (SP-001), the cost of a collection per space (SP-002), process identity (SP-003), and how sandbox and permission settings layer (SP-004). The results are in docs/internals/hooks.md, docs/internals/install.md and docs/internals/memory.md. Gemini and Antigravity CLI are out of scope (D-20).
  2. Phase 1: spaces, pins and an enforcing guard. Done: the spaces policy with nested roots and operator-only apply (SP-020 to SP-022, D-15, D-25), per-job GitHub accounts (SP-063, D-18), session pins and caller resolution (SP-010, SP-011), the tool hooks (SP-012), target extraction (SP-013) and the command log (SP-014). To do: retention (SP-015), reading the log (SP-016), session liveness (SP-017), the guard decision (SP-040), the fail-closed guard (SP-041), self-protection (SP-042), the live GitHub guard (SP-043), policy replay over the SP-001 fixtures in CI (SP-047), enforcement switches (SP-070) and minimal app controls (SP-072).
  3. Phase 2: spaces in memory. Origin and space on every write (SP-023), a Qdrant collection per space (SP-024), enforcement on every read path (SP-025), other bleed paths (SP-026), relabelling with labels_v (SP-027), quarantine (SP-028), derived content and taint (SP-029), the public write gate (SP-030), visibility (SP-031) and retagging a source (SP-071).
  4. Phase 3: outbound terms and OS sandbox. Terms per space (SP-044), the git-hook helper (SP-045), per-space harness settings and the launcher (SP-046), and refusal events (SP-048).
  5. Phase 4: the Spaces pane. RPCs, overview, setup wizard, advanced editors, Activity and Review, and CLI parity (SP-050 to SP-055), as in spaces-ui-design.html.
  6. Phase 5: feeds and interop. Slack and Teams connectors (SP-060 to SP-062), an optional OpenAPPA label source (SP-064) and documentation consolidation (SP-065).

The questions this document left open were settled on 8 Nov 2026.

  1. Default guard mode: "Block other jobs". Strict is opt-in, and the mode is configurable in the UI (D-12).
  2. A collection per space, plus public and quarantine collections, with the payload filter as a second layer (D-10). The measured search cost was accepted: 1.5× to 1.9× the p95 of one filtered collection, about +15 ms per hybrid search on 40,000 chunks (D-24).
  3. Log contents: the full command text, credential-redacted and capped at 2 KB, plus targets and the decision (D-17).
  4. Per-space harness profiles: both. orch keeps a local settings file in every checkout under a space's roots, and the optional launcher orch run <space> -- claude|codex gives a session the full profile from any folder (D-23).
  5. OpenAPPA: don't adopt it as a component now. Copy its patterns, and consider an orch label source later (D-13, SP-064).
  6. When to enforce: from the first release, with every layer switchable, rather than after a log-only period (D-11).
